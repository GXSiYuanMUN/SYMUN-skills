# 实战记录：一次完整的搬迁与三个月后的复核

> 数据来自实际执行。已脱敏（不包含用户名、服务器地址、项目名），只保留可复用的量级与结论。

## 一、搬迁前的现场

Windows 10，NTFS，三块盘：

| 盘 | 总量 | 剩余 | 使用率 |
|---|---|---|---|
| C: | 201 GB | **1.2 GB** | ≈100% |
| D: | 158 GB | 11 GB | 93% |
| E: | 118 GB | 17 GB | 87% |

C 盘 1.2 GB 属于"随时会出事"的状态（连一次系统更新都装不下）。而可搬的东西有：

| 位置 | 体积 | 性质 |
|---|---|---|
| `C:\Users\<user>\.workbuddy` | **4.8 GB** | 运行态主体 |
| `%LOCALAPPDATA%\ms-playwright` | **1.4 GB** | 浏览器内核 |
| 合计 | **约 6.2 GB** | |

另有 `%APPDATA%\WorkBuddy`（72 MB）、`CodeBuddyExtension`（112 MB）、`.codebuddy`（28 KB）—— 收益小、风险相对高，**本次不动**。

## 二、选盘：为什么不是 D

D 剩 11 GB、E 剩 17 GB。搬 6.2 GB 后：

| 盘 | 搬完剩余 | 判断 |
|---|---|---|
| D: | 约 5 GB | 太紧，且 D 装着全部历史工作区、本身在长 |
| E: | 约 11 GB | 有余量 |

**结论：资产在 D，运行态在 E。** 这本身就是合理分工 —— 运行态是会持续膨胀的机器数据，不该跟作品抢同一个盘的最后几个 GB。

## 三、执行数据

| 项目 | 实测 |
|---|---|
| 第一遍全量复制 | 19,138 个目录 / 84,711 个文件 / 4.645 GB |
| 耗时 | **1 分 24 秒**（≈59 MB/s 有效，含大量小文件） |
| 失败文件 | 3 个 —— 全是运行中的 live 数据库文件，第二遍补齐 |
| 目标盘写入基准 | D 292 MB/s、E 253 MB/s（选盘时空间优先于这点差距） |
| 切换耗时 | 十余秒（增量同步 + 改名 + 建联接 + 校验） |
| C 盘释放 | 约 6 GB（清理旧副本后） |

> 耗时经验：**小文件多的时候，实际吞吐远低于顺序写入基准**。85k 文件跑出 59 MB/s 属于正常，不要拿 SSD 的 500 MB/s 去估算。

## 四、切换后的状态

```
C:\Users\<user>\.workbuddy            目录联接 → E:\<Root>\_runtime\workbuddy
%LOCALAPPDATA%\ms-playwright          目录联接 → E:\<Root>\_runtime\ms-playwright
*.workbuddy_old / *ms-playwright_old  已清理，不存在
```

**联接透明性的硬证据**：迁移后启动的 Git Bash 进程，其可执行文件实际位于
`E:\<安装目录>\...\vendor\PortableGit` —— 也就是 `~/.workbuddy\vendor\PortableGit` 经联接解析后的真实位置。程序完全没察觉。

## 五、五天后与一个月后的复核

**第五天复核（含一次版本升级）**

| 检查项 | 结果 |
|---|---|
| 两个联接仍在位 | ✅ `os.readlink` 能读出目标 |
| `_old` 已清理 | ✅ C 盘原目录已消失 |
| 程序升级到新版本 | ✅ **联接未被破坏**，新版自有的 SQLite 迁移照常落在新盘 |
| 新版进程实际运行位置 | ✅ 在新盘（路径穿透完全透明） |

**一个月后复核：C 盘从 1.2 GB 只回升到 2.0 GB。**

搬走 6.2 GB，理论上应该回到 7 GB 左右。差额去哪了？系统更新、其他软件安装、休眠文件重新长出。这是本次最重要的一条教训：

> **搬迁是止血，不是治本。** 它精准解决"某个应用长期膨胀"这一项，不能替代全网盘盘点。
> 三个月后再看，C 盘回到 11 GB —— 期间也没再碰过 WorkBuddy 的目录，说明搬迁本身是稳的，只是别的东西在长。

## 六、附带发现的问题

**1. "任务丢了"是假象。** 数据库里有 13 条未删除的自动化，全部按 `cwds[0]` 绑在三个不同工作区上。当时所在的工作区不在任何一个 `cwds` 里 —— 所以界面空空的，但任务一条没少。

**2. 存在重复定义。** 两条同名任务，同工作区、同计划（每天同一时刻），一条是旧 `automation-<时间戳>` 形态、一条是新 uuid 形态。**有重复执行风险**，应只保留一条。

**3. 档案缺失不等于任务坏了。** 13 条里 11 条有运行档案，2 条没有 —— 那两条从未在绑定工作区里落过档，属正常，只是会丢历史上下文。

## 七、可复用的结论

1. **先量再动**：`diagnose.py` 30 秒就能给出"要不要搬、能腾多少"的答案。
2. **两遍法是必须的**：一遍在程序运行时复制（省时间），一遍在完全退出后增量（保正确）。
3. **切换脚本不要手写**：路径、编码、回滚分支，三处都极易出错。用 `make_bat.py` 生成，出错概率最低。
4. **判断联接用 `os.readlink()`**，不要用 `os.path.islink()`（对 junction 返回 `False`）。
5. **搬完要反哺**：把"哪层在哪、怎么验证"写进常驻记忆或技能，否则下个会话又要经历一遍"东西是不是丢了"的怀疑。
