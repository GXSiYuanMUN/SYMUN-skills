# 判断与选型：该不该搬、搬到哪、怎么命名

## 一、先判断：到底要不要动

| 信号 | 阈值 | 结论 |
|---|---|---|
| 系统盘剩余空间 | `< 15%` | 该处理 |
| 系统盘剩余空间 | `< 5 GB` | **立刻处理**，属于随时会出事的状态 |
| 单个可搬目录 | `> 3 GB` | 值得单独搬 |
| 系统盘上的工作数据总量 | `> 10 GB` | 整体迁移，别零敲碎打 |

跑 `python scripts/diagnose.py` 就能直接得到这些数字。

## 二、别急着搬：先清一轮可再生成的东西

**Windows 上最大的空间黑洞往往不是"你的文件"。** 接近满盘时先做这四件事，经常一次就够，根本不用搬：

| 目标 | 做法 | 典型回收 |
|---|---|---|
| 临时文件 | 磁盘清理 `cleanmgr` → 勾选"临时文件""Windows 更新清理" | 5–30 GB |
| 旧系统 | `cleanmgr` → "以前的 Windows 安装" | 10–20 GB |
| 休眠文件 | 管理员 cmd：`powercfg /h off`（不用休眠就关） | ≈ 内存大小的 40–100% |
| 包管理器缓存 | `pip cache purge`、`npm cache clean --force`、`conda clean -a` | 1–10 GB |
| 应用缓存 | 浏览器缓存、`AppData\Local\Temp` | 1–5 GB |

**只有清完仍然紧张，才进入搬迁流程** —— 搬迁是"止血"，清缓存是"减重"，两者不冲突但顺序应该反过来。

## 三、选哪个盘

| 判据 | 要求 | 原因 |
|---|---|---|
| 盘类型 | **FIXED（固定盘）** | junction 指向移动盘，拔盘即废 |
| 剩余空间 | `> 待搬体积 × 3` | 留出运行态继续膨胀的余量 |
| 文件系统 | NTFS | junction 只支持 NTFS |
| 位置 | 尽量不与"每天在长的资产"同盘 | 运行态会持续膨胀，别跟作品抢空间 |

判断盘类型（`diagnose.py` 已内置）：`GetDriveTypeW` 返回 `3` 是固定盘，`2` 是可移动盘。

**实测教训**：本机当时 C 剩 1.2 GB、D 剩 11 GB、E 剩 17 GB，搬 6.2 GB。选 E 而不是 D，因为 D 装着全部历史工作区且本身在长 —— 塞进去只剩 5 GB，等于把 C 盘的病挪到 D 盘。

## 四、命名规则（这一节别跳）

### 4.1 工作空间根目录

| 规则 | 说明 | 好例子 | 坏例子 |
|---|---|---|---|
| 只用 ASCII 字母、数字、`-` | 禁空格、禁中文 | `D:\FutureWay` | `D:\future way`、`D:\我的空间` |
| 2–20 字符，能自解释 | 别缩到看不懂 | `E:\AIHome` | `E:\x`、`E:\tmp2` |
| 非系统盘根下一级 | 不嵌进别的软件目录 | `D:\FutureWay` | `D:\Program Files\x` |
| 不以 `.` 开头 | 点开头是隐藏/程序专用 | — | `D:\.space` |
| 总路径 ≤ 150 字符 | Windows 硬限 260，要给 `node_modules`、venv 留余量 | — | 五层中文长目录 |

**为什么禁空格和中文**：`robocopy`、`mklink`、`cmd` 的引号与代码页问题都从这来。路径里带空格时每一处都得加引号，漏一处就断；批处理文件又是按系统 ANSI 码页解析的，非 ASCII 路径在别人机器上极易变乱码。

> 现实折中：Windows 用户名可能是中文（`C:\Users\张三`），这时路径里非 ASCII 无法避免。`make_bat.py` 会自动按系统 ANSI 编码写 `.bat` 以适配这种情况，但**你自己新建的目录**仍应遵守 ASCII 规则。

### 4.2 子目录

两类前缀，各管一摊，**永不复用**：

| 前缀 | 含义 | 例子 |
|---|---|---|
| `NN_` | 资产（人看的、要长期保存的） | `00_宪法`、`04_项目`、`99_归档` |
| `_` | 机器数据（会膨胀、可重建） | `_runtime`、`_logs` |

```
<Root>\
├─ _runtime\            ← 运行态：目录联接的目标都在这里
│  ├─ workbuddy\
│  ├─ ms-playwright\
│  └─ _logs\            ← 迁移日志，保留最近 30 天即可
├─ 00_宪法\              ← 协作准则、SOUL / IDENTITY / USER
├─ 01_技能\
├─ 02_记忆\
├─ 03_资产\
├─ 04_项目\
├─ 05_自动化\
└─ 99_归档\              ← 旧工作区整包留存，只读
```

三条布局原则：

1. **编号前缀**：让资源管理器按用途排序，而不是按创建时间乱序。
2. **归档不动**：旧工作区整包放 `99_归档\`，**不要改名或重排内部结构** —— 路径一变，历史会话索引和自动化绑定就断。
3. **一个家**：同一类东西只允许有一个位置。发现第二处，要么合并要么删。

## 五、什么算"工作空间的一部分"

很多人以为工作空间就是项目文件夹，其实至少四类，处置方式不同：

| 类别 | 典型位置（Windows） | 处置 |
|---|---|---|
| 项目与产物 | 自定工作目录 | 直接 robocopy 到新盘；建议同时建联接留住旧路径 |
| 运行态（技能 / 记忆 / 自动化库） | `C:\Users\<你>\.workbuddy` | **搬走 + 在原位建目录联接**（程序写死了路径） |
| 浏览器与自动化内核 | `AppData\Local\ms-playwright`、各 debug-profile | 同上传法；清掉会丢登录态 |
| 虚拟环境 / 运行缓存 | `AppData\Local\Programs`、venv、包管理器 | 重装到新盘比搬更干净 |

## 六、收益排序（哪块最值得先搬）

按"体积大 + 无登录态 + 可重建"排序，投入产出比从高到低：

1. `~/.workbuddy/binaries`（托管 Python / Node 运行时）—— 常常 1 GB 以上
2. `AppData\Local\ms-playwright` —— 浏览器内核，1 GB 上下
3. 浏览器 debug profile（`edge-debug-profile` 等）—— 可搬，但**清掉会丢登录态**，搬而不删
4. `traces/`、Crashpad 崩溃转储、`clipboard-images` —— 直接删，不必搬
5. `AppData\Roaming\<App>`、扩展目录 —— 收益小、风险相对高，通常不动

## 七、不该用这套方案的情况

- `Program Files` 下的注册表安装型软件 → 卸载重装到新盘更干净
- 数据库服务的数据目录（有服务依赖、有事务日志）→ 用程序自带的 `datadir` 配置
- 跨平台（macOS / Linux）→ 本方案依赖 NTFS + junction
- 目录正在被高频写入且无法停机 → 先做两遍复制，切换时仍必须停机
